# Pathle development versions and mobile update checks

## Release identity

The main menu shows a compact **tappable** build label at the top center,
between Settings and the DEV toggle:

**DEV · v1.5.58**

**The sole release-version source is `version.json`.** The installed
`js/version.js` constant, the main-menu fallback label, versioned
navigation links and asset query fingerprints are generated by
`node scripts/sync-release.cjs --write`. Never edit those copies manually.
GitHub Actions runs `--check` and rejects changes with stale generated
files or asset URLs. Pages continues to serve this development branch.

## How the player checks

- Opening the main menu makes a **silent, read-only** request to
  `version.json` on the same origin. A small dot appears beside the
  version label if a newer published version is available.
- Tapping the version label opens a short status dialog and triggers
  a fresh check, with a **Check again** action.
- If a newer release exists, the player can choose **Load vX.Y.Z**.
  Nothing reloads automatically; the button only works from the home
  menu, not while the game is active.
- If offline or the manifest is missing/malformed, show a safe retry
  message rather than claiming that the current build is the newest.
- The update request uses `cache:'no-store'` and a unique query
  parameter; the voluntary navigation appends `pathle-update=vX.Y.Z`
  to the same-origin page URL to bypass cached HTML.
- Updates do not write to or clear IndexedDB. Completed Daily and
  Treasure Hunt progress stays at the **same domain**.

**Important:** Existing Android shortcuts opened on the older v1.4.0
page lack the new checker. Refresh once to load v1.5.0. Subsequent
published versions can be detected by the v1.5.0 checker.

## One-command release procedure

1. Make and test a change on `pathle-modular-dev` only.
2. Update **only** the `version` field in `version.json` (e.g. `1.5.43` → `1.5.44`).
3. Run `node scripts/sync-release.cjs --write`. This automatically updates
   the installed version module, fallback labels, same-origin menu URLs,
   CSS/JS/image asset fingerprints and regression assertions.
4. Run `node scripts/sync-release.cjs --check`, then
   `node --test tests/*.test.cjs`.
5. Commit the updated source and generated files **together** to
   `pathle-modular-dev`. Check that both GitHub Actions regression tests
   and GitHub Pages deployment finish successfully before Android testing.

The synchronizer is deterministic and idempotent. Running `--write` twice
without changing source files produces no new differences. The `--check`
mode never writes files; it explains which files need synchronization.

### Caching strategy

- Each local JavaScript, CSS and image reference in the two HTML pages
  has `?v=<12-hex-content-hash>`, derived from its Git blob SHA. Unchanged
  resources keep the same URL and can remain cached across releases.
- The home and Treasure Hunt **HTML** entry URLs use the release number;
  intentional returns and explicit update installs also use the existing
  fresh-query fallback to avoid a stale GitHub Pages HTML page on Android.
- The published `version.json` is fetched with `cache:'no-store'` and a
  unique query parameter for version discovery. The game never forcibly
  reloads while a level is running.
- Navigation stays on the same origin. IndexedDB and local saves are not
  cleared, invalidated or migrated by the release script.

### Release limitations

- GitHub Pages is still configured for deployment from the development
  branch. The synchronizer runs **before committing**; the check workflow
  enforces consistency but does not itself publish or alter the branch.
- Asset fingerprinting covers the local `src`/`href` references present
  directly in `index.html` and `treasure-hunt.html`. Image URLs written
  only inside CSS or runtime JavaScript are not yet rewritten automatically;
  review such URLs when replacing in-place artwork.
- Changing files **without incrementing `version.json`** can still produce
  new content fingerprints, but the update prompt discovers new releases
  by manifest version. Therefore bump the manifest for each player-facing
  update.
- Do not change `main` without approval.
